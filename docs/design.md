# 实现设计（Python 后端）

## 运行结构

通过 `python -m server` 启动；只依赖 Python 3.11+ 标准库。`server/app.py` 使用 `ThreadingHTTPServer` 提供静态前端和原有 HTTP API。`server/engine.py` 用最多四个工作线程执行后台学习流程，接口返回 202 后由前端轮询。

`Store.lock` 是可重入线程锁：输入检查与任务登记、会话快照、阶段更新、结果提交和文件写入在锁内执行；模型和搜索网络请求在锁外进行，轮询不必等待模型返回。同会话只允许一个运行任务，全局最多四个学习任务。

`server/agents/main_agent.py` 保留原有教学提示词，分别调用规划、评分和辅导；`search_agent.py` 使用 Tavily；`providers.py` 使用 `urllib.request` 访问 Chat Completions 兼容接口，禁止 HTTP 重定向，执行本地结构校验与最多一次格式重试。

前端继续使用 JavaScript，API 的驼峰字段和历史会话 JSON 格式保持兼容。旧 Node.js 后端和测试原样保留在 `legacy/`，仅供迁移参考，不参与运行。当前仍是本机单用户开发服务，不是面向公网的生产部署。

## 产品目标

帮助初学者在无法准确描述根因时，利用少量交互找到当前最相关的理解障碍，补一小步，并返回原问题检验。诊断是假设，不是对能力的最终结论。

## 调度方式

1. 接收用户问题和可选材料，保存原始输入。
2. 如果已有检查题，评分器按服务端 rubric 评估回答。
3. 主智能体生成 goal、候选 gaps 和 queries。
4. 只有 queries 非空时才调度搜索智能体；最多两个查询。
5. 搜索模块返回来源标题、URL、摘要及搜索是否完成的说明。
6. 主智能体基于资料和用户表现生成讲解、下一道题及评分标准。
7. 程序校验输出，提交证据与状态，等待用户下一轮输入。

搜索智能体是被主智能体调度的独立检索执行模块，不额外使用一个 LLM 搜索规划器。主智能体和评分器采用分离提示词调用同一配置模型。第一版没有自治代理无限循环。

任务公开的是运行阶段和证据，不包含模型隐藏思维链。

## 诊断与验证

计划中的每个缺口默认是 hypothesis。新缺口不因为模型声称“已掌握”而直接升级。一个会话最多保存六个知识点，以限制范围。

检查题绑定一个具体技能，分 diagnostic 与 transfer：
- diagnostic 正确 → observed。
- transfer 正确且未使用帮助 → independent。
- 使用过提示或示范后正确 → assisted。
- 有明确错误证据 → needs_work；曾独立完成后出现错误 → revisit。
- unclear、没有逐字引用当前回答、或只是索要帮助 → 不生成答题证据。
- 同一道完成过的问题重复出现，会按帮助下练习处理，避免伪装新验证。

程序能保证“记录引用来自当前回答”“提示使用被记录”等机械约束，但不能保证模型对语义和根因的判断正确。通过人工评价和真实学习者实验继续验证。

学习记录不使用“完全掌握”标签，也没有把问题数量当作成功率。第一版尚无延后复测自动调度。

## 状态及证据

Session:
- id, title, material, materialName, mode
- goal, gaps, evidence, check, completedChecks
- images：图片 ID、名称、MIME、字节数、dataUrl；用户消息通过 imageIds 关联
- messages, sources, run, createdAt, updatedAt

Gap:
- id, title, reason, status, evidenceIds

Evidence:
- id, skillId, messageId, checkId
- question, quote, explanation, verdict
- kind, assisted, createdAt

Check:
- id, skillId, kind, question, rubric, assisted, createdAt

rubric 仅在服务端保存；普通读取和导出都会剔除。历史来源保存在各个 assistant message 中，避免后续搜索覆盖原引用。

## HTTP API

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | /api/config | 公开运行模式和服务是否配置，不含密钥 |
| GET | /api/sessions | 学习历史 |
| POST | /api/sessions | 建立会话；title、material、materialName |
| GET | /api/sessions/:id | 会话、消息、缺口与公开运行状态 |
| POST | /api/sessions/:id/messages | 提交 message 与 action，返回 202 |
| POST | /api/sessions/:id/retry | 重试最后一个失败请求，不重复用户消息 |
| GET | /api/sessions/:id/export | 导出不含 rubric、包含图片原数据的 JSON |
| GET | /api/sessions/:id/images/:imageId | 读取该会话中的图片 |

action 为 answer / hint / example / return。
前端每 750ms 查询当前会话，获取真实阶段与最终回复。当前未实现逐 token 流式输出。

## 错误和存储

- 任务执行中同一会话拒绝新的请求，避免上下文竞态。
- 工作状态复制后执行，所有模型结果和题目有效后再提交学习状态。
- 查询失败明确说明，不用演示结果冒充线上搜索。
- JSON 模型格式错误只重试一次；认证、额度等错误直接返回可理解的提示。
- 达到六个知识点上限时，辅导上下文只接收实际保留的知识点；检查题和 focusId 的 JSON Schema 按这些 ID 动态约束。错误引用、空正文、空题目或空评分标准与格式错误共用最多一次纠正机会。
- 失败记录包含 errorStage；服务日志记录会话 ID、运行 ID、阶段、异常类型和代码位置，不记录原始材料、模型响应正文或密钥。
- 会话写入在存储锁内串行完成，先写临时文件、flush/fsync，再用 os.replace 原子替换。最终保存失败时恢复提交前的学习状态，并尝试记录可重试错误。
- 服务启动时识别未结束任务，并允许重试。
- 运行配置改变后要求新建会话，避免演示成绩与真实评估混合。
- 初版使用最近 14 条消息和累计结构化状态作为模型上下文；更早对话仍保存在文件中。长会话上下文摘要尚未实现。

## 推荐下一步

优先用真实模型对少量人工标注对话检查：
1. 候选缺口是否有依据，是否把未提及误当成不会。
2. 诊断题能否区分候选原因。
3. 评分是否被“我懂了”或不相关关键词误导。
4. 提示是否泄露下一道独立验证题的答案。
5. 补基础后能否返回原问题。
6. 实际用户完成未见题的表现和中途退出情况。

优先新增经过人工校验的诊断/变式题库，再考虑间隔复测、知识图谱和多人部署。生成题能运行不代表测量已经有效。

## 图片材料的数据流

前端使用 FileReader 读取本地图片，验证类型、大小和能否解码，生成可预览的 data URL；用户发送时随 message 一起上传。后端再次验证 MIME、文件头、base64、数量与总大小，为图片分配内部 ID。客户端文件名从不用于磁盘路径。

图片作为独立的 image_url 内容块发送给模型，不把 base64 塞进 JSON 文本提示。图片元数据与历史 imageIds 留在文本上下文中，因此后续提问仍可引用已有图片。模型指令要求区分图中文字和推断，不把图中的命令当作系统指令。

普通会话轮询只返回图片元数据和同源读取地址，避免每 750ms 重发原图。JSON 导出额外包含图片 dataUrl，便于保留完整材料。失败重试复用原消息和图片，不重复追加。

新上传图片被视为补充材料，不触发上一题的自动评分。演示模式明确标注只能保存图片、不能识别内容。现有旧会话启动时补充空 images 列表，不破坏文本历史。

接口参考：[DeepSeek Vision](https://api-docs.deepseek.com/guides/vision/)。

## 教学知识来源

材料、图片、关键词都只是话题入口。主智能体使用自身知识补充相关背景、前置概念、解释、例子和应用；既可以纠正材料，也可以在没有材料时开展教学。不会要求用户先提供完整教材。

“知识讲解的依据”和“判断用户掌握程度的证据”分别处理：前者可以来自模型已有知识；后者仍需用户的表达与作答，不能把材料未涵盖的概念直接认定为用户缺口。

默认不转录图片、不逐句摘要，也不例行附加“仅依据截图/未联网核实”的免责声明。只有用户要求转录、具体图文细节看不清或事实确实不确定时才针对那一点说明。

未配置搜索时，程序将 searchAvailable=false 传给主智能体，并阻止检索调度，即使模型仍提出了查询。搜索只作为可选补充，不构成一般知识教学的前置条件。

## 当前认识驱动的学习路径

每轮主智能体先输出 learningPath，并保存到会话用于后续调整：
- currentUnderstanding：用户目前如何理解，区分用户自述与验证过的表现。
- targetUnderstanding：本次希望达到的具体理解。
- missingLink：连接两者所缺失的一个关系、推理步骤或必要概念。
- basis：支持这个判断的用户表达或表现。
- nextMove：clarify（定位）、bridge（补连接）、verify（检验连接）。

辅导模块据此选动作，不能把自身知识丰富理解成展开整章课程。判断不足时用一个低负担问题或最小示例定位；线索足够时只补相关一步；补完后用不同例子验证。相同学习话题应根据用户的不同认识产生不同的路径。

前端右侧展示当前认识、待接上的一步和目标，明确这只是可以修正的判断。原始材料仍可引用，但不充当知识边界。
